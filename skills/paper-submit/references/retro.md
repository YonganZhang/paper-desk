# 投稿复盘：把问题变成技能

每次投完一批（或中途出了事故），都复盘一次。目标是让下一次投稿更快、更少出错。做法是把这次遇到的问题归到类别，修类别层面的规则，不给单个案例打补丁。

## 1. 记录

投稿过程中随手记，复盘时整理成一张表：

| 问题 | 发生在哪个系统、哪一步 | 耽误多久 | 用户介入了几次 | 怎么解决的 |
|---|---|---|---|---|

同时记下每个阶段的起止时间（见 SKILL.md 的流程表）。下次判断该优化哪一段，就看这些数据。

## 2. 归类

先问：这个问题换一个期刊、一篇稿子，还会不会发生？然后归到下面的类别。

| 类别 | 判断问题 | 典型修法 | 落点 |
|---|---|---|---|
| 不可逆动作 | 是否在没批准的情况下，碰到了提交、付费、签署这类动作？ | 在系统 reference 写明终点动作；自动化在倒数第二步停下 | SKILL.md 不变量 1 + 系统 reference |
| 系统与清单不一致 | 系统存下来的东西是否和投稿包不一样？ | 回读核对项加一条 | review-gate.md |
| 身份与邮箱 | 账号、邮箱读不到、重复、借用 | 邮箱方案表加规则 | preflight.md |
| 文书规范 | 文书是否没走写作规范的全流程？ | 在写作规范里补必读项 | SKILL.md 不变量 4 |
| 期刊要求 | 是否装配后才发现期刊要求不同？ | 准备阶段的核对项加一条 | preflight.md |
| 系统怪癖 | 只在某个系统出现的页面行为 | 写进该系统 reference 的「坑与对策」 | systems/*.md |
| 重复机械操作 | 同一串操作做了三次以上 | 写成脚本，在 reference 里挂上 | scripts/ |
| 状态误判 | 是否把当前页面当成了真实状态？ | 改为从列表页确认，脚本里固化 | SKILL.md 不变量 5 + 脚本 |
| 证据口径 | 是否凭邮件、链接表现或别人的自述下了结论？ | 写明以哪一页为准 | review-gate.md、systems/*.md |
| 单篇事实 | 只对这一篇稿子成立 | 不写进技能 | 论文项目的投稿记录 |

一个问题可能同时属于两类，例如既是系统怪癖，又是不可逆动作。这时两处都改：通用规则写进不变量，具体页面写进系统 reference。

## 3. 写成规则

- 每条规则写成「条件 → 做法 → 为什么 → 边界」。具体期刊只作「示例」，每条至多两个；不写人名、稿号和账号。
- 先搜技能里有没有相近的规则。有就改原来那条，不另起一条重复的。
- 系统 reference 都按 `systems/_template.md` 的结构写。新系统第一次投完，就照模板建一份，标明实测到哪一步。
- 有代表性的坑同步进 pitfalls.md 的总表，正文只保留「为什么」。

## 4. 验证与提交

- 拿这次的真实场景回放：按新规则走，能不能挡住这次的问题？
- 想一个相邻场景，确认新规则不会误伤，例如修订稿提交、换刊重投。
- 检查引用：新增或改名的脚本在 SKILL.md 或 references 里有引用，没有孤儿脚本；文档里提到的路径都存在。
- 在技能所在仓库按明确路径提交，提交说明写清改了哪一类规则。
