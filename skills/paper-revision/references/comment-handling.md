# 拆意见与写回复

第 2 步（拆意见、出计划）和第 5 步（写回复）读本页。语气、不采纳和疑难情形见 [tone-and-cases.md](tone-and-cases.md)。

## 对照表（第 2 步交给用户）

用中文，一条意见一行：

| 编号 | 意见摘要 | 类型 | 风险 | 动作 | 改动位置 | 状态 |
|---|---|---|---|---|---|---|
| R1.3 | 文献综述偏旧 | 文献 | 低 | 补近 5 年相关文献并核实 | Section 1 | 待改 |
| R2.4 | 补模块消融实验 | 补实验 | 高 | 补充材料新增 Table S3 | Supplementary | 待作者提供 |
| R1.12 | 建议合并第 4、5 节 | 结构 | 中 | 不采纳，补过渡段 | Section 5 | 待改 |

- **编号**：编辑意见用 AE（或 E.1、E.2），审稿人用 R1.1、R1.2……；审稿人原文自己带编号时沿用其编号。一段意见里有多个要求时拆成多行（R1.2a、R1.2b），回复时在同一条回复里逐一回应。注意区分两种计数：决定信里的原意见条数（传给 `--expect-comments`）和对照表的行数（含拆分子项和删除记录），两者通常不相等。
- **类型**：文字表达、结构、文献、方法说明、补实验或分析、统计、数据与材料、图表、格式、伦理与合规、不采纳。
- **风险**：高 = 补实验、统计质疑、伦理/数据完整性、核心结论被挑战；中 = 结构调整、主张强度、审稿人之间冲突；低 = 措辞、格式、补文献。高风险条目先做，并先和作者确认方向。
- **动作和改动位置**每行都要填：每条意见都对应一处正文改动（见下节），"不采纳"也写出折中改动。
- **状态**：待改、已改、待作者提供、不采纳。"已改"要有对应证据：新增或改写的在标红稿里有红字，纯删除的有删除记录。
- **删除**：单独记一行，写清删了什么、在哪、为什么。
- 多个审稿人提同一件事时，在后出现的条目里写"见 R1.5"，回复信里同样交叉引用，不重复长篇回答。

### 类型 → 默认动作

| 类型 | 默认动作 |
|---|---|
| 文字表达、术语 | 改句子；同类说法全文统一改 |
| 结构 | 调整或补过渡；不采纳时说明理由并做折中改动 |
| 文献 | 只加真正相关且已核实存在的文献；审稿人点名的文献先评估相关性 |
| 方法说明 | 把答案写进方法节（补参数、定义、流程） |
| 补实验或分析 | 作者提供结果后写进正文或补充材料；做不到的走 tone-and-cases.md「做不到的实验」 |
| 统计 | 向作者要检验名称、样本单位、样本量、效应量或置信区间、多重比较校正；不编数字 |
| 主张过强 | 降低措辞强度，全文同步；必要时补 Limitations |
| 伦理、合规、数据完整性 | 一律"待作者提供"，按作者给的事实写；缺事实不能交付 |
| 纯肯定 | 致谢，不改稿（见下节"例外"） |

## 每条都改正文

每条意见在正文里至少有一处对应改动，回复里写明改在哪、改了什么，并贴出改后原文。为什么：这是对审稿人的尊重，审稿人读回复时先看"改了没有"；只解释不改稿的回复容易被看作敷衍，下一轮常被追问。

- 改动大小与意见分量相称。重要意见实改；不太重要、或者没能完全做到的，也做小幅改动：补一句澄清、限定条件、术语定义、过渡句，或在 Limitations 里补一句。
- 审稿人只是提问、正文本身没错：把答案写进正文（补一句说明），再在回复里贴出。审稿人读到这里有疑问，读者多半也会有。
- 不采纳：给出折中改动（见 [回复信格式](response-letter-format.md) 的"回复写法"），同样贴出。
- 删除也算改动：在回复里用一句话写明删了什么（用 deleted / removed 表述）。
- 多个审稿人提同一件事：后一条交叉引用前一条，写明改动所在位置，如 "Please see our response to R1.5 (Section 2.3)."
- 例外：没有提出任何要求的意见（纯肯定、"no further comments"）不改稿，在回复信该条回复后单独一行写 `<!-- no-change: 理由 -->` 声明；编辑的笼统要求（"请按审稿意见修改"）指向下面的逐条回复即可。

`scripts/build_response_docx.py` 逐条检查：审稿人条目找不到改动证据（`[[ ]]` 改后原文、新贴的图表、删除说明、交叉引用或 no-change 声明）时报 BLOCK，编辑条目只报 WARN；JSON 里的 `manuscript_changes` 列出每类证据的条数和全部 no-change 声明，交付前过目一遍，确认声明的确实是纯肯定意见。

## 回复的组织

- 编辑意见放最前。编辑汇总了多个审稿问题时，把它拆成 (1)、(2)… 逐点简答，每点用 "— Addressed in R1.3 (Section 2)" 指向审稿人条目。
- 每条回复的顺序：回应关切 → 做了什么 → 改在哪里 → 贴改后原文。
- 改后原文直接从修改后的稿件复制，不凭记忆重写；贴出后由 `build_response_docx.py --manuscript-text` 核对。
- 需要新结果的条目，作者没给数据之前，回复里不写具体数字，对照表标"待作者提供"。
- 审稿人要求的工作确实做不到时：说明具体原因，给出替代证据或收窄结论，并在 Limitations 里写清。

## 措辞

- 致谢一条只说一次，并且针对这条意见的内容：纠错类 "Thank you for the careful observation."，建议类 "Thank you for this suggestion."，提问类 "Thank you for the question."；不要每条都用同一句。
- 同意时直接说做了什么；不同意时先说明建议的合理之处，再给理由和折中改动。
- 措辞类意见（说法过强、术语不准）：承认问题，改成有证据支持的说法，并说明全文同类说法一起改了。
- 不出现指责审稿人误解的说法；如果审稿人确实误解了，先检查是不是稿件写得不清楚，并改稿件。
